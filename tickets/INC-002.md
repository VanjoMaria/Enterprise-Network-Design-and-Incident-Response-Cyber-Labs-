# Incident Ticket — INC-002

| Field | Detail |
|---|---|
| **Ticket ID** | INC-002 |
| **Title** | Branch WAN link failure — OSPF automatic reroute via Backup WAN Router |
| **Reported by** | Network Engineer (deliberate fault injection — scheduled DR/redundancy test) |
| **Affected site** | Branch Office |
| **Severity** | High (simulated) — a real occurrence would isolate the branch office from HQ if redundancy failed |
| **Status** | Resolved — redundancy confirmed working as designed |

---

## Summary

The primary WAN link between Branch Router and Edge Router was deliberately shut down to simulate a real-world link failure (cut cable, carrier outage, etc.), in order to prove that OSPF automatically reroutes Branch traffic over the Backup WAN Router path with no manual intervention, satisfying the design requirement that *"the branch office must stay connected even if the primary WAN link fails."*

---

## Symptoms (expected, as this was a controlled test)

- Branch Router's OSPF adjacency with Edge Router (Router ID `203.0.113.1`) transitions from `FULL` to `DOWN`.
- Branch Router's routing table loses all routes learned via the primary path.
- Without working redundancy, this would mean total loss of connectivity between Branch and HQ (and the internet, since Branch relies on HQ's single NAT exit point).

---

## Diagnostic Steps & Evidence

### 1. Baseline — confirm primary path is active before the fault

```
Router(config)#do sh ip route ospf
O   10.10.10.0 [110/66] via 10.255.255.13, 00:19:12, Serial0/0/0
O   10.10.20.0 [110/66] via 10.255.255.13, 00:19:12, Serial0/0/0
O   10.10.30.0 [110/66] via 10.255.255.13, 00:19:12, Serial0/0/0
O*E2 0.0.0.0/0  [110/1]  via 10.255.255.13, 00:48:02, Serial0/0/0

Router(config)#do sh ip ospf neighbor
Neighbor ID       Pri  State    Address          Interface
203.0.113.1       0    FULL/ -  10.255.255.13    Serial0/0/0
10.255.255.17     0    FULL/ -  10.255.255.17    Serial0/0/1
```
All HQ-bound routes are using the **primary path** (via `10.255.255.13`, cost 66), with both OSPF neighbors — Edge Router and Backup WAN Router — healthy and `FULL`.

### 2. Fault injection — shut down the primary WAN link

The primary interface on Branch Router (`Serial0/0/0`) was administratively shut down to simulate a real link failure.

### 3. Confirm OSPF detected the failure

```
%LINK-3-UPDOWN: Interface Serial0/0/0, changed state to down
%LINEPROTO-5-UPDOWN: Line protocol on Interface Serial0/0/0, changed state to down
01:02:40: %OSPF-5-ADJCHG: Process 1, Nbr 203.0.113.1 on Serial0/0/0 from FULL to DOWN,
Neighbor Down: Interface down or detached
```
OSPF immediately flagged the loss of the primary neighbor.

### 4. Confirm automatic reroute via the Backup WAN Router

```
Router(config)#do sh ip ospf neighbor
Neighbor ID       Pri  State    Address          Interface
10.255.255.17     0    FULL/ -  10.255.255.17    Serial0/0/1

Router(config)#do sh ip route ospf
O   10.10.10.0 [110/130] via 10.255.255.17, 00:00:59, Serial0/0/1
O   10.10.20.0 [110/130] via 10.255.255.17, 00:00:59, Serial0/0/1
O   10.10.30.0 [110/130] via 10.255.255.17, 00:00:59, Serial0/0/1
O*E2 0.0.0.0/0  [110/1]  via 10.255.255.17, 00:00:59, Serial0/0/1
```
Only the Backup WAN Router neighbor remains, and every route to HQ — including the default route for internet access — automatically shifted to the backup path, with a higher OSPF cost (130 vs. the original 66), confirming it is correctly treated as a secondary route rather than a preferred/load-balanced one.

### 5. Confirm connectivity actually survived, not just the routing table

From a Branch-side PC (PC7):
```
C:\>ping 10.10.10.6
Reply from 10.10.10.6: bytes=32 time=1ms TTL=125
Reply from 10.10.10.6: bytes=32 time=1ms TTL=125
Reply from 10.10.10.6: bytes=32 time=1ms TTL=125
Reply from 10.10.10.6: bytes=32 time=1ms TTL=125
Packets: Sent = 4, Received = 4, Lost = 0 (0% loss)
```
A second ping run immediately after shows slightly higher latency (up to 31ms vs. 1ms) but still **0% packet loss** — consistent with traffic now taking the longer backup path through the Backup WAN Router, while remaining fully functional. This is the key proof: the branch PC never lost reachability to an HQ host (Sales VLAN, `10.10.10.6`) at any point during the failure.

### 6. Restore the primary link and confirm reversion

```
%LINK-5-CHANGED: Interface Serial0/0/0, changed state to up
%LINEPROTO-5-UPDOWN: Line protocol on Interface Serial0/0/0, changed state to up
01:04:59: %OSPF-5-ADJCHG: Process 1, Nbr 203.0.113.1 on Serial0/0/0 from LOADING to FULL,
Loading Done

Router(config)#do sh ip ospf neighbor
Neighbor ID       Pri  State    Address          Interface
203.0.113.1       0    FULL/ -  10.255.255.13    Serial0/0/0
10.255.255.17     0    FULL/ -  10.255.255.17    Serial0/0/1

Router(config)#do sh ip route ospf
O   10.10.10.0 [110/66] via 10.255.255.13, 00:00:08, Serial0/0/0
O   10.10.20.0 [110/66] via 10.255.255.13, 00:00:08, Serial0/0/0
O   10.10.30.0 [110/66] via 10.255.255.13, 00:00:08, Serial0/0/0
O*E2 0.0.0.0/0  [110/1]  via 10.255.255.13, 00:00:08, Serial0/0/0
```
Once the primary link came back up, OSPF re-established the adjacency and automatically reverted all routes back to the lower-cost primary path — confirming the backup path is genuinely a *fallback*, not a permanent change, and that the network self-heals in both directions without manual route manipulation.

---

## Root Cause

Not applicable — this was a planned, deliberate fault injection to validate existing redundancy design, not an unplanned outage.

---

## Resolution

No remediation was required beyond restoring the shut interface (`no shutdown`), since the network behaved exactly as designed: OSPF detected the primary link failure within seconds, automatically rerouted all Branch-to-HQ traffic (including the default internet route) over the Backup WAN Router, and reverted cleanly once the primary link was restored.

---

## Prevention / Design Notes

- This test validates requirement: *"The branch office must stay connected even if the primary WAN link fails."*
- The cost differential between the primary (66) and backup (130) paths is working as intended — OSPF prefers the primary path when available and only uses the backup under genuine failure conditions, rather than load-balancing across both (which would complicate troubleshooting and give unpredictable latency under normal conditions).
- **Recommendation for production deployment:** configure OSPF timers (hello/dead intervals) more aggressively than defaults if sub-second failover is a business requirement — the default dead-timer interval introduces a brief (several-second) connectivity gap during convergence, which did not cause failed pings in this test but could affect latency-sensitive applications (VoIP, video) in a real deployment.
- This test also indirectly re-confirms the OSPF full-mesh fix applied earlier in the build (INC-related to the Core A↔Core B missing adjacency) — a healthy, fully-converged OSPF domain was a prerequisite for this failover to work cleanly.
